# BootStrap Wall3t — Cryptographic Protocol for Quarantine Reversal

**Status:** protocol draft for security review
**Purpose:** authorize a user-only reversal of an active quarantine without exposing wallet keys or reintroducing per-transaction approvals
**Recommended authenticator:** WebAuthn/FIDO2 hardware-backed administrator credential using ES256/P-256 or another deployed, audited WebAuthn algorithm

## 1. Security objective

A quarantine reversal is a rare control-plane action. It is not an approval for a transaction, and it does not authorize the agent to execute anything. It only changes the global deny registry from `ACTIVE` to `REVERSED` at a new registry version after the user reviews evidence and proves control of an enrolled hardware-backed administrator credential.

The protocol must prevent:

- an agent from reversing a quarantine;
- replay of an old valid reversal assertion;
- use of a valid assertion for a different quarantine, registry, or user;
- rollback to a pre-quarantine registry version;
- approval after the registry head changed during review;
- phishing through a different origin or relying-party identifier;
- database operators bypassing the user authorization path;
- accidental reactivation of old positive allow decisions after reversal.

## 2. Keys and trust domains

Keep these keys separate:

| Key | Holder | Purpose | Must not be used for |
|---|---|---|---|
| Hardware admin credential | User hardware authenticator | Prove user authorization for reversal | Wallet transaction signing, agent capability, registry signing |
| Registry signing key | Registry HSM | Sign checkpoints and trust-bundle metadata | User identity or wallet transactions |
| Registry node identity keys | Registry nodes | mTLS and consensus membership | User authorization or checkpoint authority unless explicitly part of the quorum certificate |
| Wallet signer keys | Secrets Vault / hardware wallets | Sign blockchain transactions | Registry control-plane actions |
| Extension/session keys | Browser extension or platform session | Authenticate the local control plane | Direct reversal authority without hardware assertion |

The hardware admin credential is a separate administrative principal. A blockchain wallet signature alone is not sufficient because it creates chain-specific coupling, can be phished by a dApp, and does not prove control of the intended user device or relying party.

## 3. Recommended cryptographic profile

### Primary profile: WebAuthn/FIDO2

- Credential: discoverable or non-discoverable hardware-backed credential.
- Signature algorithm: ES256 (`alg = -7`, ECDSA P-256 with SHA-256) for broad authenticator support.
- User verification: required (`UV=1`); user presence is also required by the authenticator flags.
- Relying-party id: a dedicated stable value such as `auth.bootstrap-wall3t.example`, not a dApp origin.
- Origin: the controlled extension/app origin registered for the product.
- Challenge: 32 random bytes generated by the registry authorization service.
- Credential id and public key: enrolled through an authenticated user setup ceremony and stored in the Secrets Vault/identity service, not in the registry event log.
- Counter handling: enforce authenticator signature-counter policy where supported; detect rollback or clone signals and require re-enrollment or an additional credential.

WebAuthn's signed data includes the authenticator data and client-data hash. The service must verify the relying-party hash, origin, challenge, type, flags, algorithm, signature, and counter behavior. Do not accept a bare ECDSA signature stripped from its WebAuthn envelope.

### Optional high-assurance profile

For environments requiring multiple administrators or recovery resilience, enroll `n` hardware credentials and require a threshold policy such as 2-of-3 for reversal. The threshold is applied to independent WebAuthn assertions over the same authorization digest. It is not implemented by asking one authenticator to sign a mutable list.

## 4. Enrollment protocol

Enrollment is a user setup action and must be separate from reversal.

1. The user authenticates to the extension using the existing account/session mechanism.
2. The registry authorization service issues an enrollment challenge containing a random nonce, user id, registry id, protocol version, and expiry.
3. The browser calls `navigator.credentials.create()` with the dedicated RP id, user-verification requirement, allowed algorithms, and an explicit user display name.
4. The hardware authenticator creates the credential key internally and returns the credential id, attestation object, and client data.
5. The service verifies origin, RP id hash, challenge, flags, attestation policy, and public key algorithm.
6. The service stores a credential record:

```text
AdminCredential {
  credential_id,
  user_id,
  rp_id,
  public_key,
  algorithm,
  aaguid_or_attestation_class,
  sign_count,
  created_at,
  last_used_at,
  status: ACTIVE | SUSPENDED | REVOKED,
  protocol_version,
}
```

7. The service signs an enrollment receipt and emits an audit event. The private key never leaves the authenticator.
8. Recovery credentials must be enrolled before a primary credential is lost. Recovery enrollment itself requires existing user authorization or a separately governed recovery ceremony; it cannot be created by an agent.

Attestation policy should start conservatively. If device provenance is not required, use privacy-preserving attestation while still requiring hardware-backed user verification. Do not claim that WebAuthn attestation proves a device is uncompromised.

## 5. Reversal authorization transcript

The service and client use canonical CBOR or a canonical binary encoding. JSON stringification is not used as the signature transcript because field ordering and number representations must not be ambiguous.

### Step A — Fetch and review

The user requests reversal for `quarantine_id`. The service returns the active record, current certified registry head, evidence hashes and metadata, affected entity, scope, reason, reporter, and downstream impact. The extension renders this data in a non-dApp-controlled origin.

The service creates a one-time `ReversalChallenge`:

```text
ReversalChallenge {
  protocol = "bootstrap-wall3t/quarantine-reversal/v1",
  challenge_nonce,              // 32 random bytes
  authorization_id,             // unique request id
  user_id,
  registry_id,
  quarantine_id,
  active_record_hash,
  expected_registry_version,
  expected_state_root,
  evidence_review_hash,
  requested_action = "REVERSE_QUARANTINE",
  issued_at,
  expires_at,                   // short lifetime, e.g. 120 seconds
  credential_policy_hash,
}
```

`active_record_hash` commits to the exact record reviewed. `expected_registry_version` and `expected_state_root` prevent a user from authorizing against a stale screen. `evidence_review_hash` commits to the evidence set and the review result shown to the user.

### Step B — Canonical authorization digest

Construct:

```text
authorization_digest = SHA-256(
  "bootstrap-wall3t/quarantine-reversal/v1" ||
  0x00 || canonical_encode(ReversalChallenge)
)
```

The challenge sent to WebAuthn is a fresh random challenge bound to `authorization_id`; the server stores the mapping from that challenge to the canonical authorization digest. Do not put sensitive evidence or raw secrets into the WebAuthn challenge.

### Step C — Hardware assertion

The extension calls `navigator.credentials.get()` with:

```text
publicKey = {
  challenge: webauthn_challenge,
  rpId: dedicated_rp_id,
  allowCredentials: [enrolled_credential_id],
  userVerification: "required",
  extensions: { /* only audited, explicitly supported extensions */ }
}
```

The authenticator returns `clientDataJSON`, `authenticatorData`, and `signature`. The client forwards the complete assertion to the authorization service. The client is not trusted to verify its own assertion.

### Step D — Server verification

The authorization service verifies, in order:

1. `authorization_id` exists, is unused, and has not expired.
2. The user session is bound to the intended `user_id`.
3. `clientData.type == "webauthn.get"`.
4. The client challenge equals the server-issued challenge for this authorization id.
5. The origin is the registered extension/app origin.
6. The RP id hash in authenticator data equals the dedicated RP id.
7. The user-verification flag is set; reject if policy requires UV and it is absent.
8. The user-presence flag is set.
9. The credential id is enrolled, active, and belongs to the same user.
10. The algorithm is allowed and the signature verifies over `authenticatorData || SHA-256(clientDataJSON)`.
11. The counter is acceptable under the authenticator's clone-detection policy.
12. The challenge's registry version, state root, active-record hash, and evidence-review hash still match the certified current head.
13. No emergency freeze, credential suspension, or user-account lock is active.

A valid assertion produces an internal `VerifiedHardwareAuthorization` object. Raw WebAuthn material is not passed to the consensus state machine as authority.

## 6. Atomic reversal commit

The authorization service submits a deterministic `ReverseQuarantine` command to the registry leader:

```text
ReverseQuarantine {
  command_id = authorization_id,
  expected_version,
  quarantine_id,
  user_identity = user_id,
  verified_credential_id,
  hardware_assertion_hash,
  evidence_review_hash,
  authorization_digest,
  submitted_at,
}
```

The state machine atomically checks:

- the command id has not been used;
- the expected version equals the committed head;
- the quarantine exists and is active;
- the user identity matches the credential owner;
- the authorization digest was verified by the authorization service;
- the command's canonical bytes match the authorization transcript;
- the reversal policy still permits this scope.

If any check fails, the command is rejected and the user must start a new challenge. The state machine then appends the reversal as a new registry version:

```text
ACTIVE(version N) -> REVERSED(version N+1)
```

The registry signs a new checkpoint and publishes the commit receipt. Existing simulation and signing tickets remain invalid because their registry version is older than `N+1`.

## 7. Audit record

The audit event stores:

```text
QuarantineReversalAudit {
  authorization_id,
  command_id,
  user_id,
  quarantine_id,
  prior_registry_version,
  new_registry_version,
  prior_state_root,
  new_state_root,
  active_record_hash,
  evidence_review_hash,
  authorization_digest,
  credential_id_hash,
  authenticator_aaguid_or_class,
  user_verification = true,
  user_presence = true,
  sign_counter_result,
  committed_checkpoint_hash,
  created_at,
}
```

Do not store raw client data, raw WebAuthn signatures, private keys, recovery secrets, or evidence contents in the general audit stream. Store content hashes and access-controlled references instead.

## 8. Replay, rollback, and phishing defenses

- **One-time authorization id:** mark it consumed only after a successful commit; failed attempts remain auditable and cannot be retried with the same authorization.
- **Short expiry:** expire challenges quickly and require a fresh review after timeout.
- **Expected head binding:** any report, reversal, or unrelated registry update between review and commit invalidates the challenge.
- **Domain separation:** protocol string, registry id, action, version, and entity are committed into the digest.
- **Origin and RP binding:** a lookalike dApp or extension cannot reuse the assertion because the RP id and origin differ.
- **User verification:** require PIN, biometric, or equivalent hardware UV according to authenticator policy.
- **No client-side authority:** the server verifies the complete WebAuthn transcript and the registry leader enforces the expected version.
- **Key rotation:** credential suspension/revocation is itself a user-authorized identity event and is checked before reversal.
- **Registry key separation:** a registry checkpoint signature cannot satisfy a hardware authorization check, and a hardware assertion cannot sign a registry checkpoint.
- **Rollback detection:** monotonic versions, previous-checkpoint hashes, quorum certificates, and trust-bundle rotation prevent a restored old database from being accepted as current.

## 9. Recovery and incident response

If a hardware credential is lost, the user uses an already enrolled recovery credential or a separately governed recovery process. A support operator must not directly insert a reversal row. If all credentials are lost, the registry enters a user-controlled recovery freeze; recovery requires the documented identity and hardware ceremony, with all actions audited.

If a credential is suspected compromised:

1. suspend it immediately;
2. freeze reversals for that user if policy requires;
3. rotate/revoke the credential in the identity service;
4. review recent assertions and reversal events;
5. enroll a replacement credential through the surviving recovery path;
6. rotate registry trust material if the authorization service itself was compromised.

A compromised browser extension should not be able to silently reverse a quarantine because hardware user verification, RP binding, evidence review, expected-head binding, and the registry state machine all remain necessary.

## 10. Protocol test vectors and release gates

Before implementation is accepted, test with deterministic fixtures for:

1. valid ES256 assertion with UV and UP flags;
2. wrong origin;
3. wrong RP id hash;
4. wrong challenge;
5. expired challenge;
6. reused authorization id;
7. changed quarantine record hash;
8. changed registry version between review and commit;
9. invalid user verification flag;
10. unknown or revoked credential;
11. counter rollback / clone signal;
12. invalid signature;
13. mismatched command bytes;
14. registry leader failover during commit;
15. duplicate command delivery;
16. reversal of an already reversed or nonexistent record;
17. checkpoint signed by an untrusted key;
18. stale checkpoint presented at wallet-core sign and broadcast;
19. registry signing key rotation during an active challenge;
20. two-of-three threshold policy with one invalid assertion.

The protocol is complete only when these tests run against the authorization service, registry state machine, signed checkpoint verifier, and wallet-core read barrier together.

## Protocol summary

```text
review current record
  -> receive one-time, head-bound challenge
  -> hardware WebAuthn assertion with UV/UP
  -> server verifies origin, RP, credential, signature, counter, expiry
  -> registry leader verifies expected head and active record
  -> quorum commits reversal at version N+1
  -> registry emits signed checkpoint
  -> all old tickets and positive caches become stale
```

The protocol changes one global deny decision only after explicit user hardware authorization. It never grants an agent access to the parent wallet, the Financial Cold Vault, or raw key material.
