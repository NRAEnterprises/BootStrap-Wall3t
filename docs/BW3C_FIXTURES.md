# BW3C Cross-Language Fixture Vectors

The checked-in fixture [`fixtures/bw3c/evm_transaction_intent_v1.json`](../fixtures/bw3c/evm_transaction_intent_v1.json) is generated by the Rust wallet-core canonical encoder for `BW3C` wire version `1`, record kind `7` (`EvmTransactionIntent`). It contains no keys, credentials, RPC endpoints, or signed transactions.

The vector binds the following deterministic fields:

- Agent principal `agent-fixture-1` and wallet `wallet-fixture-1`.
- EVM chain ID `1`.
- Sender and target are raw 20-byte values: `11` repeated 20 times and `22` repeated 20 times. The JSON fixture writes these values as 40 hexadecimal characters without a `0x` prefix.
- Nonce `7`, value `9`, gas limit `100000`.
- EIP-1559 max fee `2` and priority fee `1`.
- Calldata `0xaabbcc`.
- Policy, capability, and document identifiers.
- Contract, chain, and wallet footprint entities in this fixture's Rust `EntityRef` ordering.
- Validity window `1700000000` through `1700000600`.

## Canonical byte layout

The canonical transcript is concatenated in this exact order. All fixed-width integers are unsigned big-endian values; `u32` prefixes count bytes, not characters.

```text
ASCII "BW3C"
u16 wire version (1)
u8 record kind (7)
u32+UTF-8 intent_id
u32+UTF-8 wallet_id
u8 principal discriminant (2 = agent), then u32+UTF-8 agent_id
u8 operation discriminant (2 = contract call)
u64 chain_id
20 raw sender bytes
u8 target-present flag (1), then 20 raw target bytes
u64 nonce
32-byte big-endian value
u64 gas_limit
u8 fee discriminant (2 = EIP-1559)
32-byte max_fee_per_gas
32-byte max_priority_fee_per_gas
u32+calldata bytes
u8 deployment-present flag (0 = absent in this fixture)
u32+UTF-8 policy_id
u32+UTF-8 capability_id
u32+UTF-8 document_hash
u32 footprint count
footprint entities in this fixture's Contract, Chain, Wallet order
u64 not_before_unix
u64 expires_at_unix
```

Footprint entity encoding is `u8 discriminant` followed by the entity payload. Contract is discriminant `2` plus `u64 chain_id` and `u32+UTF-8 address`; Chain is discriminant `5` plus `u64 chain_id`; Wallet is discriminant `8` plus `u64 chain_id` and `u32+UTF-8 address`. Rust validation requires the footprint to already be sorted and deduplicated; the serializer preserves that validated vector order and does not sort it while encoding. These footprint addresses are intentionally serialized as the 40-character ASCII strings shown in the fixture, matching Rust `EntityRef` encoding; they are not raw 20-byte EVM addresses.

Expected values:

```text
record kind:             7
intent digest SHA-256:   74bdcab9ad7743ff37567874bceb8b0333aa8d8bc6b425c93bd65e1b1f3a3708
```

## Verification commands

Rust regenerates the reference vector and compares it byte-for-byte:

```bash
cargo run --manifest-path rust/wallet-core/Cargo.toml \
  --example generate_evm_fixture \
  > /tmp/wall3t-rust-fixture.json
cmp /tmp/wall3t-rust-fixture.json fixtures/bw3c/evm_transaction_intent_v1.json
```

Python independently encodes the fields and verifies the full bytes and digest:

```bash
pytest -q bootstrap_wall3t/tests/test_bw3c_fixture.py
```

Elixir independently encodes the fields with Erlang crypto SHA-256:

```bash
cd elixir/wall3t_orchestrator
mix test test/bw3c_fixture_test.exs
```

TypeScript independently encodes the fields and verifies them with Web Crypto:

```bash
cd extension/policy-boundary
npx tsc --noEmit
npx tsc --outDir /tmp/wall3t-ts-fixture --noEmit false
node /tmp/wall3t-ts-fixture/test/index.test.js
```

The fixture is an interoperability test vector, not an authorization ticket. Production signing still requires the authenticated wallet-core gate, BWAU envelope, registry-version checks, and vault/HSM signer boundary described in [`WALLET_CORE_GATE_PROTOCOL.md`](WALLET_CORE_GATE_PROTOCOL.md).

## BWAU authenticated ticket vector

[`fixtures/bwau/evm_simulation_ticket_v1.json`](../fixtures/bwau/evm_simulation_ticket_v1.json)
is the first authenticated transport vector. It contains the exact BWAU
envelope bytes, BWAU signed message, payload hash, complete ticket transcript,
ticket signature, and the corresponding Ed25519 **public** key. The fixture was
generated with an ephemeral in-memory test signer; no private signing material
is present in the repository.

The vector is intentionally split into two signatures. The BWAU signature binds
the canonical BW3C payload and generic envelope context. `ticket_signature`
binds the request ID, chain ID, policy/capability/wallet identities,
simulation hash, and every other Python transport field not carried by generic
BWAU. Consumers must verify both signatures against an independently provisioned
public-key registry and must never accept a public key from the ticket.

Python verification is executable today:

```bash
pytest -q bootstrap_wall3t/tests/test_bwau_fixture.py
```

Rust, Elixir, and TypeScript consumers must use the exact hex fields in this
vector for their authenticated-wire compatibility tests. The vector does not
authorize chain activity, disclose credentials, or replace the production
registry, replay store, or vault/HSM boundary.
