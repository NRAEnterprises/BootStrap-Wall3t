# BootStrap Wall3t — Build Plan and Review Baseline

**Status:** Review baseline and implementation plan
**Reviewed:** 2026-11-18
**Repository baseline:** `abb8fb2` (`main`)
**Project name:** BootStrap Wall3t

> This document is the project root of truth for architecture decisions, implementation phases, audit gates, and progress. Every new architectural capability must add or update a dated entry here before the corresponding implementation is considered complete.

## 1. Product definition

BootStrap Wall3t is a browser-extension-style, self-custody wallet with one user wallet and multiple agent wallets. Agent wallets are linked to a user-controlled parent wallet, may be generated by the parent wallet, and may be assigned to shared or dedicated automation scopes. The wallet also provides chain discovery, target discovery, policy-controlled transaction execution, and reusable automation templates.

The product must preserve these boundaries:

- The user remains the authority over root wallet creation, recovery, agent creation, permissions, spending limits, and revocation.
- Agents submit explicit, typed intents; they do not receive raw seed material or unrestricted signer access.
- The Rust wallet core is the signing and policy trust boundary.
- The Elixir runtime supervises workflows and long-lived agents but cannot access raw keys.
- The TypeScript extension is a presentation and user-consent surface, not a secret store.
- Third-party RPCs, explorers, token lists, bridges, notification providers, and dApps are untrusted inputs.
- Unknown contracts, undecodable signatures, ambiguous chain context, stale quotes, and unverifiable state fail closed.

## 3. Current-state findings

### Release blockers in the GitHub prototype

These findings are baseline evidence, not a final security audit:

- `bootstrap_wall3t/wallet/key_manager.py` explicitly uses placeholder mnemonic generation, non-BIP-32 derivation, and mock address derivation. This is a critical seed/key blocker.
- `bootstrap_wall3t/wallet/tx_routes.py` accepts `mnemonic` in `TxSignRequest`. A secret must never cross the browser/API boundary. This is a critical secret-handling blocker.
- `bootstrap_wall3t/wallet/agent_wallet.py` invokes `docker exec`, uses fallback/mock keys, and returns a locally generated hash as a transaction hash. This is not a signing or broadcast implementation.
- `bootstrap_wall3t/wallet/tx_routes.py` describes create/sign/broadcast as mock flows and derives a key from request data.
- `bootstrap_wallet/server/main.py` defaults to `DEV_TOKEN` and `JWT_SECRET`, implements a handwritten JWT verifier, allows wildcard methods/headers and a wildcard-like extension origin with credentials, and uses process-local rate limiting. These fail the production API boundary until replaced.
- `node_manager/manager.py` exposes shell-backed Docker control through HTTP. It needs a narrowly allowlisted privileged service or must be removed from the wallet API.
- `docker-compose.yaml` exposes node and Lightning ports broadly, runs development/insecure modes, includes `latest`-style operational assumptions, and contains a mainnet Lightning configuration. It is not a production deployment manifest.
- `bootstrap_wall3t/vault/pqc_key_vault.py` claims RAM-only handling but persists an encrypted ledger and uses Python object/string boundaries that do not prove zeroization or `mlock` coverage. PQC algorithms do not replace a complete operational key custody design.
- The current repo contains `__pycache__` artifacts and documentation claims paths/features that are absent from the repository. Supply-chain and reproducibility work is required.

### Gaps in the remake skeleton

- Rust traits and types are a good starting boundary, but the default runtime returns zero balances, empty supported chains, placeholder errors, or placeholder transaction hashes.
- `VaultStore`, state stores, Solana/Cosmos contracts, native bindings, Zig bridge code, and benchmark code contain placeholders.
- No concrete parent-wallet/agent-wallet graph, capability delegation, assignment model, revocation model, or inheritance rules are specified.
- No canonical intent schema, simulation result schema, approval inventory, clear-signing format, chain-scoped nonce model, or transaction state machine is defined.
- No RPC allowlist/proxy implementation, provider quorum/divergence logic, explorer data integrity path, notification signing, dApp session security, or discovery safety model is implemented.
- The Elixir project has no dependency declarations or complete application behavior in the supplied archive.
- The extension/UI has no manifest, secure messaging protocol, permission UX, or end-to-end consent tests.
- Strategy files are unclassified and must not become executable automation templates without review, normalization, backtesting, and risk limits.

## 4. Target architecture

### 4.1 Trust boundaries

```text
Browser extension UI
  └─ authenticated local/extension messaging
      └─ Policy/API facade (no secrets)
          └─ Elixir agent runtime (workflow supervision only)
              └─ Rust wallet service (typed intents, simulation, policy, signer)
                  ├─ chain adapters and validated RPC clients
                  ├─ encrypted state and wallet graph metadata
                  └─ isolated signer/vault interface
```

The Rust service must expose opaque wallet and agent identifiers, public addresses, policy decisions, simulations, receipts, and audit records—not seeds, private keys, raw keystore bytes, or unrestricted signer handles.

### 4.2 Wallet graph and capabilities

The domain model must include:

- `UserWallet`: root ownership, recovery metadata, supported chains, and global policy.
- `AgentWallet`: a derived or independently provisioned signer identity linked to one user wallet.
- `AgentAssignment`: many-to-many relationship between agents, wallets, workflows, and scopes.
- `Capability`: explicit permissions such as read-only discovery, quote, simulation, exact transfer, bounded swap, or template execution.
- `Policy`: chain, contract, asset, amount, frequency, slippage, fee, time-window, and approval constraints.
- `Revocation`: immediate disablement of an agent, capability, session, template, contract, provider, or chain.
- `AuditEvent`: append-only record of who/what requested, simulated, approved, signed, broadcast, or revoked an action.

Default relationship: an agent has no write capability. A user must explicitly grant a capability with an expiry and spending/risk bounds. Multiple agents may be assigned to the same wallet only through a conflict-aware policy evaluator and independent per-agent budgets.

### 4.3 Language allocation

- **Rust:** wallet graph, key derivation interfaces, signer isolation, transaction intent and simulation, policy, address/chain validation, adapters, state machine, audit events, and FFI boundary.
- **Elixir:** supervision tree, scheduling, workflow execution, retries, monitors, discovery jobs, and template orchestration. It handles opaque IDs and signed capability tokens only.
- **TypeScript:** extension UI, discovery views, policy authoring, simulation rendering, session management, and user consent. It never stores seeds or private keys in ordinary extension storage.
- **Solidity/Sway/Solana/Cosmos-native languages:** only contracts that are actually required; each contract and transitive dependency gets its own audit scope.
- **Zig/C/C++:** only after profiling proves a bottleneck or platform integration need. No placeholder native path is part of the critical security path.
- **Python:** offline tooling, migration, test fixtures, research analysis, and controlled strategy normalization only.

## 5. Staged implementation roadmap

Each phase has an exit gate. A phase is not complete because code compiles; its evidence must be recorded in this document and in tests/reports.

### Phase 0 — Governance and repository hygiene

**Deliverables:** this build plan; architecture decision record format; contributor/security policy; reproducible toolchain files; secret scanning; removal of generated artifacts; CI skeleton; audit control registry.

**Exit gate:** clean repository, pinned toolchains/dependencies, CI runs lint/typecheck/unit tests, no secret findings, and every audit control has an owner and evidence location.

### Phase 1 — Domain model and threat model

**Deliverables:** wallet graph schema; capability/delegation model; agent assignment semantics; revocation model; canonical identifiers; threat model; data classification; state-transition diagrams.

**Exit gate:** user wallet can create/disable agents in a purely in-memory test domain; no transaction signing yet; policy tests cover least privilege, expiry, shared-wallet conflicts, and revocation.

### Phase 2 — Rust wallet trust boundary

**Deliverables:** Rust workspace; typed `TxIntent`; chain-scoped `AccountRef`, `Address`, `AssetId`, `Nonce`, `FeeQuote`; canonical serialization; signer trait; opaque key handles; strict error taxonomy; audit event emission; state machine.

**Exit gate:** no raw key or mnemonic crosses a public API; unit/property tests prove intent hash stability, chain ID binding, address validation, signer refusal on unsupported/undecodable operations, and exact reviewed-vs-signed payload equality.

### Phase 3 — Key custody and recovery

**Deliverables:** standard mnemonic/derivation implementation using reviewed libraries; per-chain derivation registry; encrypted-at-rest keystore; OS/HSM/secure-enclave integration plan; memory exposure controls; recovery and wipe procedures; seed-generation provenance records.

**Exit gate:** clean-device recovery tests for every initially supported chain; CAT1 and CHAIN6 critical controls have evidence; no claims of post-quantum protection without reviewed implementations and clear threat-model limits.

### Phase 4 — First chain adapter and validated RPC

**Deliverables:** one EVM testnet adapter; chain registry; per-chain ABI/address registry; nonce/fee handling; two-provider RPC quorum; response validation; timeouts; request bounds; authenticated proxy; metrics and divergence alerts.

**Exit gate:** testnet create/simulate/sign/broadcast/receipt flow with chain ID and nonce isolation; RPC critical controls pass or are explicitly blocked; no mainnet support yet.

### Phase 5 — Simulation, approvals, and clear signing

**Deliverables:** independent simulation; asset-flow diff; calldata and EIP-712 decoder; exact approvals by default; Permit/Permit2/setApprovalForAll handling; approval inventory/revocation; unknown-contract default deny; high-value human gate; post-execution reconciliation.

**Exit gate:** TX1/TX2 and CAT4 critical controls have executable tests; malicious fixtures cover selector collisions, hidden recipients, stale permits, changed state between simulation and execution, and chain replay.

### Phase 6 — Elixir automation runtime and templates

**Deliverables:** supervised agent processes; workflow DSL/schema; capability-token handoff; idempotency keys; retries with backoff; rate/budget controls; pause/kill/revoke; durable run history; template registry.

Initial templates should be policy-authorized and autonomous: balance/position monitor, alert-on-condition, discovery watchlist, quote-and-simulate, bounded trading, scheduled transfers, and bootstrap-fund flows can run without per-transaction human approval when the user has explicitly authorized the relevant policy, capability, budget, and document set. Human involvement is required at authorization, policy change, capability escalation, and emergency intervention boundaries—not as continuous supervision of every execution.

**Exit gate:** agents can run, pause, resume, and revoke without signer access; workflow replay is deterministic; every write action has a policy decision and audit trail; approved policies can execute autonomously within their declared bounds without per-action prompts.

### Phase 7 — Browser extension and user consent UX

**Deliverables:** Manifest V3 extension; isolated UI/background messaging; origin and dApp session verification; wallet/agent views; discovery view; policy editor; simulation/approval screens; session revocation; recovery warnings; safe notifications.

**Exit gate:** VIS2/VIS3 critical controls and CAT2 UI controls are tested; extension storage contains no seed/private key; content-script messages are origin-validated; unknown or undecodable requests cannot be approved silently.

### Phase 8 — Discovery, visibility, and target onboarding

**Deliverables:** chain/contract/token discovery pipeline; provider inventory; verified/unverified labeling; raw-data fallback; staleness indicators; target risk classification; user review queue; import-to-template flow.

Discovery must be advisory, not a trusted execution source. A discovered target can only become executable after chain/address/ABI/contract graph, policy, and simulation checks.

**Exit gate:** VIS1/VIS4 critical controls have evidence; provider compromise and stale-data tests demonstrate fail-closed labeling and raw-data visibility.

### Phase 9 — Additional chains and integrations

Add chains one at a time, in this order only if justified by product evidence: additional EVM L2, Solana, Fuel, then Bitcoin/Lightning. Bridges, swaps, staking, ramps, notifications, and third-party dApp protocols are separate release tracks with separate audits.

**Exit gate:** all CHAIN controls are evaluated per chain; recovery, fee, nonce, address, provider, and agent-context tests exist per chain. A chain with an unmet critical control is removed from the release configuration.

### Phase 10 — Production hardening and release

**Deliverables:** signed/reproducible builds; hardware-backed release keys; two-person release approval; dependency/SBOM/CVE process; fuzzing/property tests; external security review; privacy/legal review; incident response; backup/restore drills; staged testnet and canary release.

**Exit gate:** no unresolved critical blocker; legal controls are reviewed by qualified counsel for each distribution jurisdiction; production configuration has no dev secrets, open RPCs, wildcard CORS, insecure admin endpoints, or mock transaction paths.

## 7. Strategy vault policy

The 5,808 strategy documents are reference material, not approved automation. They must be ingested into a separate strategy catalog with provenance, license/source metadata, asset/chain/timeframe tags, required indicators, assumptions, leverage/shorting flags, backtest status, and risk classification.

No strategy may be executable until it has:

- been normalized into a typed, deterministic template;
- passed static safety checks and bounded resource checks;
- declared allowed contracts, assets, chains, and maximum loss;
- passed historical and adversarial backtests with documented limitations;
- been attached to an explicit user capability and spending policy;
- been approved for the intended jurisdiction and release tier.

The initial product should ship discovery, monitoring, simulation, and policy-authorized autonomous execution templates. Autonomous trading is allowed within explicit user-created policies; it must not be enabled by an opaque default, an undocumented strategy, or a capability broader than the user approved.

## 8. Automation-first clarification

The human-in-the-loop requirement for this project means **human authorization of the operating envelope**, not a human click for every transaction and not continuous observation of agents. The user should be able to authorize an agent wallet to operate autonomously using a documented policy, strategy, budget, time window, chain scope, contract scope, and emergency behavior.

The required human boundaries are:

- create, recover, or link a wallet;
- grant, modify, renew, or escalate an agent capability;
- approve a policy or strategy package for autonomous use;
- change high-impact risk limits or destination allowlists;
- respond to emergency pause or recovery events when the configured circuit breaker requires it.

Within those boundaries, the agent may trade, rebalance, transfer, bootstrap funds, discover targets, and retry or schedule actions without per-action prompts, provided every action remains inside the active policy and passes the wallet-core safety gates.

## 9. Automation-first expansion proposals

These proposals extend the core product rather than turning it into a manually supervised wallet.

1. **Policy compiler and capability certificates.** Compile human-readable policies into signed, versioned capability certificates consumed by the Rust wallet core. The Elixir runtime may request execution, but only the wallet core can decide whether the certificate permits it.
2. **Agent wallet operating modes.** Support `observe`, `simulate`, `autonomous-bounded`, `autonomous-rebalancing`, and `emergency-paused` modes. Mode changes require an explicit user authorization and are visible in the wallet graph.
3. **Budget lanes.** Give each agent independent budgets for principal, gas, slippage, losses, fees, and daily/weekly turnover. Shared wallets should reserve funds per agent so one agent cannot consume another agent’s operating capital.
4. **Strategy capsules.** Package a strategy as immutable code/configuration plus its assumptions, allowed venues, required data, risk limits, version, provenance, and rollback version. Agents execute only a user-approved capsule hash.
5. **Autonomous circuit breakers.** Allow policies to define automatic pause conditions such as drawdown, abnormal slippage, provider divergence, repeated failed simulations, liquidity collapse, contract-code change, unexpected token behavior, or deviation from expected trade frequency.
6. **Policy-driven human escalation.** Human interaction should be exceptional and policy-defined: for example, pause after a 5% daily drawdown, request reauthorization after a strategy version change, or continue autonomously during ordinary execution. This preserves automation while retaining a controlled recovery boundary.
7. **Agent-to-agent treasury lanes.** Permit transfers between linked agent wallets through explicit one-way or two-way channels with limits, purpose labels, settlement windows, and reconciliation. This directly supports agents bootstrapping one another without exposing the parent wallet’s root authority.
8. **Automation escrow and staged funding.** Let the user fund an agent wallet through staged allocations: operating float, reserve, profits, and quarantine. Policies can move funds between lanes only under declared conditions, with the parent wallet retaining revocation authority.
9. **Event-triggered strategy activation.** Allow agents to activate policies from verified events such as price/volatility thresholds, liquidity changes, contract events, scheduled windows, wallet balance thresholds, or discovery signals. Every trigger must be authenticated, chain-scoped, freshness-checked, and replay-protected.
10. **Deterministic replay and shadow execution.** Before activating a policy, run it in simulation or shadow mode against recorded market/chain events. After activation, retain enough non-secret event data to replay why an action was permitted without retaining private material.
11. **Strategy portfolio coordinator.** Add a higher-level coordinator that allocates capital among agent wallets according to user-defined objectives and risk budgets. It must treat each agent as an independently constrained sub-portfolio, not as an unrestricted swarm.
12. **Discovery-to-policy pipeline.** Let discovery produce candidates, have risk and contract analysis produce evidence, and allow the user to approve a target class or policy rule rather than manually approving every target. Newly discovered contracts remain blocked until they satisfy the rule.
13. **Policy inheritance with deny-overrides.** Parent-wallet policies may establish global ceilings; agent policies may narrow them but never widen them. A global deny, quarantine, chain disablement, or emergency pause must override local agent permissions immediately.
14. **Automation observability without emotional interference.** Provide dashboards, metrics, and audit trails for review after the fact: realized P/L, policy utilization, drawdown, rejected actions, provider health, and agent behavior. Observability must not become a per-action approval queue.
15. **Safe policy upgrades.** Support scheduled policy activation, dual-version overlap, automatic rollback, and expiration. A strategy can continue operating while a replacement is tested in shadow mode, then switch atomically at a declared block/time boundary.

The first autonomous trading vertical slice should therefore be: one testnet chain, one agent wallet, one approved strategy capsule, a bounded budget, policy-compiled capabilities, deterministic simulation, autonomous execution, automatic circuit breakers, and post-run auditability.

## 10. Recommendations for review

1. **Make the wallet graph the central product model.** The differentiator is not merely a multi-chain wallet; it is controlled delegation between a user wallet, agent wallets, assignments, capabilities, and automation templates.
2. **Use capability-based permissions, not a single agent API token.** Capabilities should be chain-, contract-, asset-, amount-, frequency-, and time-bounded, independently revocable, and auditable.
3. **Adopt a two-plane design.** Keep a control plane for metadata/workflows/discovery and a data plane for signing/execution. The control plane must never be able to manufacture or extract a signer.
4. **Start with one chain and one safe write primitive.** An EVM testnet exact native-token transfer plus simulation is a better foundation than prematurely supporting EVM, Bitcoin, Solana, Fuel, bridges, swaps, staking, and Lightning together.
5. **Treat discovery as hostile input.** Discovery results should generate review candidates and risk labels, never automatic allowlist entries or executable contracts.
6. **Separate read-only, simulated, user-approved, and autonomous execution tiers.** Make the safe tier the default and require explicit promotion through policy and audit gates.
7. **Replace handwritten crypto and auth early.** Use reviewed libraries and standard formats; do not implement mnemonic, address, JWT, or signature primitives from scratch.
8. **Make transaction intent a signed artifact.** Hash the canonical intent, simulation result, policy decision, encoded transaction, and final broadcast payload; reject any mutation after the final gate.
9. **Use durable event sourcing for auditability.** Agent runs, grants, revocations, simulations, approvals, signatures, broadcasts, and receipts should be append-only and queryable without secrets.
10. **Design for degraded mode.** If RPC providers, token-risk vendors, notification services, or dApp verification are unavailable, show raw uncertainty and stop risky execution rather than showing a reassuring default.
11. **Do not market “post-quantum” as a blanket safety claim.** Document exactly which algorithms protect which artifacts, how classical chain signatures remain in scope, and what endpoint compromise still defeats.
12. **Make legal scope a product decision.** Define intended jurisdictions and supported features before adding swaps, staking, ramps, advisory language, or autonomous trading; obtain qualified counsel review before public release.
13. **Keep the name and product identity stable.** Use “BootStrap Wall3t” consistently in the repository, extension manifest, package names where practical, and user-facing documentation; avoid letting the older “Sats-Stack” prototype branding become the product identity.
